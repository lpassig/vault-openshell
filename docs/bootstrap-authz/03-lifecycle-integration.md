## Proposed credential activation contract

1. **Authorize the launch intent.** Authenticate the requester and resolve the workspace, owner or mission, policy, driver and authorized resources before minting. Mint only launch credentials with an enforced purpose and expiry. Bind them to the authorization decision, sandbox, generation and credential epoch. Treat the existing native token exchange as another way to obtain the same restricted gateway JWT.
2. **Verify the running supervisor.** Check the gateway's persisted driver and runtime reference under the current generation and ownership term. Require a fresh proof from a key enrolled through a trusted runtime path. For Kubernetes, combine the verified SPIFFE identity and registration facts with key possession. For Docker and Podman, require a trusted local host or backend to attest the launch and deliver or enroll its per-generation key through an isolated control channel. The local enrollment and channel are unverified. A container ID and a JWT issued by the gateway are insufficient evidence of caller key possession. If the policy requires device posture, missing or stale posture denies. Support for policies that explicitly omit device posture would require a separate policy choice. The existing slice requires it.
3. **Record the authorization alongside configuration admission.** Use the current push result and polling admission fences to correlate the configuration instance, policy and provider revisions. Persist a separate gateway-authored approval bound to that fence, the launch decision, owner or mission, verified runtime/key, generation, epoch, scopes and expiry. A supervisor's `Accepted` report describes configuration application. The gateway decides credential authorization independently and can deny, expire or revoke it. Use a conditional write so a replaced session or generation cannot activate credentials using an old proof.
4. **Enforce the approval at each privileged boundary.** Check it before accepting a privileged RPC or stream action, resolving a static provider value, reading a token cache, minting an OAuth assertion, issuing an extension credential, or returning a privileged refresh. Require sender binding on continued access. Invalidation must cover policy/attachment changes, revoked devices or keys, restarts, ownership changes and replica failover. Treat config push as a notification of state changes and check the authoritative record on credential use.

Verified ordering constraint: polling startup asks for provider configuration before reporting `Accepted`. Push bootstrap also builds the provider environment before a result can be reported. Requiring an accepted report before building today's credential-bearing configuration can deadlock startup. The proposed first configuration payload carries policy and credential references without values. Once the gateway has validated the acknowledgement and proof, a separate authorized update or RPC can deliver credential values. [Polling startup](../../crates/openshell-supervisor/src/lib.rs#L3232), [push bootstrap](../../crates/openshell-server/src/config_delivery/session.rs#L900).

## Review and test sequence

1. Share persisted runtime matching across native exchange and the proof gate, and reuse OCSF for routed bootstrap denials. This is implemented in the fork. New authenticated bootstrap requests also check that the durable grant is still current. Gateway JWT verification requires the issuer and verifier to agree on bootstrap mode. Revocation of an already-open configuration stream remains part of the lifecycle work. Signature and freshness checks still apply to workload proof.
2. Specify trusted key enrollment and challenge transport for Kubernetes and one local driver. Verify that enrollment material is unavailable to sandbox workloads, that launch replay cannot enroll a new key and that each proof is bound to the runtime and channel.
3. Wire the verified decision into the existing configuration lifecycle. Exercise preissued and exchanged launch credentials, push and poll, rejected configuration repair, old supervisor compatibility, restart and replica takeover. Test that configuration acknowledgement alone cannot authorize a credential and that unsupported drivers fail closed.
4. Enforce credential activation at all delivery points. Test zero privileged minting, secret reads and secret delivery before approval, after revocation and after policy or runtime replacement. Audit persistence failure through the existing OCSF request context and the separate decision record.

Verified implementation boundary. The fork enforces launch admission and the Kubernetes gateway provider path. Docker and Podman verify a supervisor at polling configuration admission and record a configuration-only decision. Production posture and supervisor enrollment integrations remain open. See [implementation notes](02-implementation.md).

## Docker SPIRE prototype

Verified. The TLS verifier uses the handshake's client certificate, validates its chain against one SPIFFE trust domain's bundle, and checks the exact expected URI and expiry at authorization time. The handshake fixture covers missing certificates, stale generations, other sandboxes, ambiguous URI SANs, another domain, and a CA trusted by the listener but outside the workload bundle. [TLS verifier](../../crates/openshell-crypto/src/tls/spiffe.rs), [handshake fixture](../../crates/openshell-crypto/tests/spiffe_client.rs), [SPIFFE validation](https://spiffe.io/docs/latest/spiffe-specs/x509-svid/#5-validation).

Verified. Docker's create RPC schedules provisioning before the supervisor exists. The existing compute-driver `GetSandbox` call accepts a request for an on-demand supervisor observation. Docker checks the running supervisor's role, identity labels and pinned image, and returns its immutable container ID with the driver-staged launch generation and epoch. Older drivers omit the observation. [Compute contract](../../proto/compute_driver.proto), [Docker inspection](../../crates/openshell-driver-docker/src/lib.rs).

Verified. `ReportSandboxConfiguration` validates the existing instance and revision fences before accepting a report. The bootstrap gate verifies the current JWT and its durable admission grant, derives the expected X.509-SVID URI from a live Docker observation, checks the peer on the same TLS connection and revalidates device, host and sandbox authorization. It records the policy decision in the existing decision store and saves a configuration-only activation annotation with the accepted report in the same compare-and-set. The annotation carries the decision expiry. The separate readiness status describes configuration application. Polling can obtain an empty provider snapshot to complete startup. [Configuration report](../../crates/openshell-server/src/grpc/policy.rs), [Enforcement](../../crates/openshell-server/src/auth/bootstrap.rs), [Decision policy](../../crates/openshell-core/src/bootstrap_authz/policy.rego).

Verified. The Kubernetes broker in #4732 obtains a stable sandbox JWT-SVID for the gateway to present to upstream OAuth. The Docker X.509 identity authenticates the supervisor on its gateway connection and identifies a specific launch. Docker activation authorizes configuration and provider attachments remain blocked. A later provider integration requires a gateway-mediated assertion format both Docker and the upstream token service support. [Broker](../../crates/openshell-spire/src/broker.rs), [Docker authorization](../../crates/openshell-server/src/auth/bootstrap.rs).

Verified. An optional Docker setting reuses the read-only Workload API socket projection for the supervisor. Each accepted configuration report fetches a fresh X.509-SVID and uses it on the report's TLS connection alongside the launch JWT. Gateway authentication still uses the configured gateway CA. The integration fixture exercises the real client and gateway over TLS with a mock Workload API and compute driver. [Docker projection](../../crates/openshell-driver-docker/src/lib.rs), [Supervisor report](../../crates/openshell-supervisor/src/lib.rs), [Gateway integration test](../../crates/openshell-server/src/grpc/provider/access_token/bootstrap_tests.rs).

Verified upstream. The SPIRE Docker workload attestor derives selectors from labels on the calling container. [SPIRE Docker attestor](https://github.com/spiffe/spire/blob/main/doc/plugin_agent_workloadattestor_docker.md).

Unverified deployment requirements. A registrar needs to bind each entry to the exact inspected launch before the launch JWT expires and remove stale registrations. Validate issuance, rotation and revocation on a live Docker host. Keep the socket directory outside user-approved workload mounts and enroll only one X.509 identity for the supervisor. Use an explicit authorized policy that requires no supervisor-authored startup changes. Local push delivery still requires integration. [SPIFFE Workload API specification](https://spiffe.io/docs/latest/spiffe-specs/spiffe_workload_api/).

## Podman SPIFFE activation

Verified implementation. Podman answers the same `GetSandbox` observation request as Docker. It reads the companion from the configured Libpod daemon and requires a running, managed supervisor with matching sandbox and workspace labels. It compares the daemon-reported root filesystem image ID to the configured supervisor image. The driver stamps the runtime generation and epoch from the authenticated launch bundle on the supervisor. [Observation](../../crates/openshell-driver-podman/src/driver.rs), [Libpod image ID](https://github.com/containers/podman/blob/v5.0.0/libpod/container_inspect.go#L140).

Verified implementation. The socket mount and its environment variable are projected into the isolated supervisor. Podman reserves the launch labels in this mode and disables sandbox host bind mounts when projecting the socket. The gateway uses the existing polling gate and requires the Podman-specific `/supervisor/podman/<container-id>` suffix. The fixture exercises the production SPIFFE mTLS report against the gateway with a mock Workload API and compute driver. [Container specs](../../crates/openshell-driver-podman/src/container.rs), [SPIFFE identity binding](../../crates/openshell-core/src/bootstrap_authz.rs), [TLS fixture](../../crates/openshell-server/src/grpc/provider/access_token/bootstrap_tests.rs).

Unverified deployment requirements. A live Podman host needs an attestor and registrar that verify the supervisor process and register the exact launch identity from trusted daemon data. Validate socket permissions, SVID issuance, and registration revocation on that host. Provider activation and session renewal still need separate local runtime integration. [Gateway configuration](../how-it-works/gateways/configuration.mdx#experimental-bootstrap-authorization).
