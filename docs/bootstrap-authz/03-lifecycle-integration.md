## Proposed credential activation contract

1. **Authorize the launch intent.** Authenticate the requester and resolve the workspace, owner or mission, policy, driver and authorized resources before minting. Mint only launch credentials with an enforced purpose and expiry. Bind them to the authorization decision, sandbox, generation and credential epoch. Treat the existing native token exchange as another way to obtain the same restricted gateway JWT.
2. **Verify the running supervisor.** Check the gateway's persisted driver and runtime reference under the current generation and ownership term. Require a fresh proof from a key enrolled through a trusted runtime path. For Kubernetes, combine the verified SPIFFE identity and registration facts with key possession. For Docker and Podman, require a trusted local host or backend to attest the launch and deliver or enroll its per-generation key through an isolated control channel. The local enrollment and channel are unverified. A container ID and a JWT issued by the gateway are insufficient evidence of caller key possession. If the policy requires device posture, missing or stale posture denies. Support for policies that explicitly omit device posture would require a separate policy choice. The existing slice requires it.
3. **Record the authorization alongside configuration admission.** Use the current push result and polling admission fences to correlate the configuration instance, policy and provider revisions. Persist a separate gateway-authored approval bound to that fence, the launch decision, owner or mission, verified runtime/key, generation, epoch, scopes and expiry. A supervisor's `Accepted` report describes configuration application. The gateway decides credential authorization independently and can deny, expire or revoke it. Use a conditional write so a replaced session or generation cannot activate credentials using an old proof.
4. **Enforce the approval at each privileged boundary.** Check it before accepting a privileged RPC or stream action, resolving a static provider value, reading a token cache, minting an OAuth assertion, issuing an extension credential, or returning a privileged refresh. Require sender binding on continued access. Invalidation must cover policy/attachment changes, revoked devices or keys, restarts, ownership changes and replica failover. Treat config push as a notification of state changes and check the authoritative record on credential use.

Verified ordering constraint: polling startup asks for provider configuration before reporting `Accepted`. Push bootstrap also builds the provider environment before a result can be reported. Requiring an accepted report before building today's credential-bearing configuration can deadlock startup. The proposed first configuration payload carries policy and credential references without values. Once the gateway has validated the acknowledgement and proof, a separate authorized update or RPC can deliver credential values. [Polling startup](../../crates/openshell-supervisor/src/lib.rs#L3232), [push bootstrap](../../crates/openshell-server/src/config_delivery/session.rs#L900).

## Review and test sequence

1. Share persisted runtime matching across native exchange and the proof gate, and reuse OCSF for routed bootstrap denials. This is implemented in the fork. New authenticated bootstrap requests also check that the durable grant is still current. Gateway JWT verification requires the issuer and verifier to agree on bootstrap mode. Revocation of an already-open configuration stream remains part of the lifecycle work. Signature and freshness checks still apply to workload proof.
2. Specify trusted key enrollment and challenge transport for Kubernetes and one local driver. Verify that enrollment material is unavailable to sandbox workloads, that launch replay cannot enroll a new key and that each proof is bound to the runtime and channel.
3. Wire the verified decision into the existing configuration lifecycle. Exercise preissued and exchanged launch credentials, push and poll, rejected configuration repair, old supervisor compatibility, restart and replica takeover. Test that configuration acknowledgement alone cannot authorize a credential and that unsupported drivers fail closed.
4. Enforce credential activation at all delivery points. Test zero privileged minting, secret reads and secret delivery before approval, after revocation and after policy or runtime replacement. Audit persistence failure through the existing OCSF request context and the separate decision record.

Verified implementation boundary: the current slice enforces launch admission and the gateway provider path. It has no gateway-authored activation record in configuration admission, local runtime verifier, production posture authority, or supervisor proof signer. A successful fixture with mock evidence does not qualify those integrations. See [implementation notes](02-implementation.md).

## Docker SPIRE prototype

The prototype has two independently tested inputs for a future activation decision. The TLS verifier uses the handshake's client certificate, validates its chain against one SPIFFE trust domain's bundle, and checks the exact expected URI and expiry at authorization time. The handshake fixture covers missing certificates, stale generations, other sandboxes, ambiguous URI SANs, another domain, and a CA trusted by the listener but outside the workload bundle. [TLS verifier](../../crates/openshell-crypto/src/tls/spiffe.rs), [handshake fixture](../../crates/openshell-crypto/tests/spiffe_client.rs), [SPIFFE validation](https://spiffe.io/docs/latest/spiffe-specs/x509-svid/#5-validation).

Docker's create RPC schedules provisioning before the supervisor exists. The existing compute-driver `GetSandbox` call now accepts a request for an on-demand supervisor observation. Docker inspects the live supervisor container, checks its role, identity labels and pinned supervisor image, and returns its immutable container ID with the driver-staged launch generation and epoch. Older drivers omit the observation. This records what the trusted Docker daemon sees and does not identify the RPC caller. [Compute contract](../../proto/compute_driver.proto), [Docker inspection](../../crates/openshell-driver-docker/src/lib.rs).

The proposed wiring joins these inputs at configuration admission. Use the authenticated JWT to look up the sandbox, compare a fresh driver observation to its current launch coordinates, and require a SPIFFE registration scoped to that launch and container. Keep the Workload API available only to the supervisor and reserve the activation identity for gateway authentication. The existing Docker provider Workload API setting also enables supervisor-local OAuth, so activation needs a separate configuration and an upstream policy that leaves credential issuance with the gateway. Both identity inputs must be available and current before policy can allow.

Live Docker and SPIRE validation, supervisor SVID acquisition, gateway integration, and the stored authorization decision are still pending. The current prototype changes neither credential issuance nor the feature flag's Kubernetes-only requirement.
